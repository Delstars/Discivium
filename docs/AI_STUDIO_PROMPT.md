# Google AI Studio prompt — Discivium frontend

You are a senior product designer and frontend engineer. Build a visually exceptional, coherent and fully navigable frontend for Discivium, an independent fictional UAE university management and learning platform. This is a Software Architecture course project, not a throwaway visual mockup.

## Repository and non-negotiable boundaries

Use Delstars/Discivium-test, starting from its default main branch. The current repository is clean and contains the Python backend, documentation and an empty ui/ destination. If branch selection is supported, use ui-redesign; otherwise commit frontend additions directly to main. Create or modify files only under ui/ (new standalone React + TypeScript + Vite frontend). Do not modify, delete or regenerate prototype/, docs/, .github/, root files, database schema or backend. Do not replace the repository with a new app scaffold. If the editor cannot preserve existing files or cannot write under ui/, export the frontend separately instead. Read docs/UI_API.md before implementation; it is the exact live API contract. The Python backend is already implemented, tested locally through automated checks and is the source of truth. Do not add Firebase, Supabase, Express, Gemini, AI, external Google Workspace, OAuth, extra databases, external fonts/CDNs or mock production data. Remove all AI coaching and assistant UI. No role-switch dropdown: authenticate as a different fictional account.

Build the frontend with relative fetch URLs, credentials:'same-origin', real session cookie, X-CSRF-Token on protected POSTs, multipart for file uploads. Vite base /ui/, dev proxy /api -> http://127.0.0.1:8000 (changeOrigin:false); output ui/dist. Use hash routing or state-based navigation. All production flows must use live API; if standalone preview requires fixtures, make a separately labelled, opt-in design-preview mode disabled by default, never silently fall back. The backend must run separately. Do not invent endpoints. On login call GET /api/state; after each successful action refetch state. Handle all HTTP errors, especially 401,403,409. Show loading, empty, disabled, confirmation, success and error states. No fake success, arbitrary IDs, optimistic grades or payments.

## Design direction
Create a premium academic operating system: calm, refined, elegant, information-rich, not a generic SaaS template. Use a responsive sidebar with a compact geometric Discivium wordmark, grouped navigation, breadcrumb, notification tray and account menu; dark navy/ink and ivory canvas with restrained indigo/teal accents, highly legible typography, consistent spacing and strong contrast. Offer light/dark themes; locally persist only appearance preferences. Use subtle transitions and icons; avoid glassmorphism, giant hero banners, excessive gradients, rainbow cards, meaningless KPIs and overdecorated charts. Make desktop layout exceptionally polished and phone/tablet usable. Keyboard accessibility, labelled inputs, focus states, tooltips, status badges, readable tables, sorting/filtering/search, empty states, modal/drawer forms, clear destructive-action confirmation.

## Role experiences
Student: overview with current modules, upcoming deadlines, attendance and actual released GPA, notification feed; course detail tabs for resources, coursework, discussion, polls; assignment list with deadline filters, actual PDF/DOCX submission, status and released feedback; registration catalogue with seat usage, prerequisites, schedule and server errors; weekly timetable; attendance history; Scholar Passport / academic record with grade distribution and downloadable fictional CSV; finance with AED amount, unpaid balance, invoice list, simulated pay confirmation and receipt state; campus services with request creation/status timeline/cancellation; advising consent with assigned advisor and shared notes. No invented data or official transcript claims.

Lecturer: teaching overview, assigned courses and weekly timetable; course resources publish/download; assignment creation including strict/allow-late policy and maximum marks; submission queue, real file download, grade and feedback form, released result workflow; student roster and attendance session creation/marking; internal course discussion and single-question poll builder, response counts and close poll. Do not imply an instructor can view another instructor's courses.

Administrator: campus overview from actual data; user directory and demo account creation; programme creation/assignment; course offering creation with room, credits, capacity, lecturer and time; enrollment and advisor assignment; invoices and payment ledger; service request queue with legal status transitions and decisions; audit history searchable by actor/action. No password or secret in read views.

Advisor: assigned students, consent badges, withheld records when consent absent, released course records, GPA, attendance and deterministic threshold flags only when permitted; shared advising notes. No finance data or guardian impersonation.

## Interaction details
Use a single typed API client, role-specific feature components, reusable layout/table/form components and typed data contracts. No direct database access or client-side permission decisions as a substitute for the server. Use clear navigation and meaningful summaries from real data. Include upload progress where available (indeterminate if unavailable), actual download links, deadline timezone labels, course timetable with day/time and responsive list view, and meaningful accessibility. Display the local demo disclaimer in a discreet footer and finance dialog. Each visible action must work against its matching endpoint or be clearly labelled not implemented and excluded from active navigation.

## Deliverables
A complete ui/ folder with package.json, lockfile if supported, vite.config.ts, index.html, src/, shared API client/types, responsive styles and README. Build must succeed using npm install and npm run build. Include a mapping of screens and actions to documented endpoints. Do not implement a backend. Do not commit generated dist or dependencies. At completion, list files changed, any screens that remain unconnected, and exact run/build instructions. Verify with real backend where possible; if Python server is not reachable inside AI Studio, say so rather than claiming integration was tested. Prioritize working end-to-end interactions and visual quality equally.
